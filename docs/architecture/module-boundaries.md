# Module Boundaries

## 目标

明确各目录的职责边界，让机器和人都知道“该改哪里，不该改哪里”。

---

## 边界表

| 区域 | 目录 | 主要职责 | 应该关心什么 | 不应该承载什么 |
|---|---|---|---|---|
| 入口层 | `web/`, 启动脚本 | HTTP 接口、页面、服务启动 | 请求接入、响应、展示 | 核心业务决策规则 |
| 编排层 | `app/` | 状态、路由、图执行、工具框架 | 任务流程与系统协调 | 具体场景实现细节、外部平台页面逻辑 |
| 场景层 | `internal_network/`, `crypto/`, `pwn/`, `reverse/`, `misc/`, `ai_security/`, `cloud_security/` | 领域节点与提示词 | 本场景特有流程 | 跨场景公共基础设施 |
| 工具层 | `tools/` | 本地工具适配、命令封装、文件生成 | 单个工具的调用协议 | 全局任务编排 |
| 远程执行层 | `remote_executor/` | 会话、SSH、WebShell、远程命令 | 连接与执行通道 | 页面展示与产品逻辑 |
| 数据层 | `data/`, 持久化文件 | 运行时数据、日志、缓存、向量库 | 数据读写与产物存放 | 业务逻辑源码 |
| 文档层 | `docs/`, `specs/`, `AGENTS.md` | 规则、设计、运行手册、需求契约 | 真正的协作规范 | 运行时状态或临时输出 |

---

## 变更边界规则

### 修改 `web/`

必须同步检查：

- 是否影响 API 暴露面
- 是否引入新的配置入口
- 是否需要更新 `docs/runbooks/security.md`

### 修改 `app/`

必须同步检查：

- 是否改变流程、状态、工具注册方式
- 是否需要更新 `docs/architecture/system-overview.md`
- 是否需要更新 `docs/architecture/module-boundaries.md`

### 修改 `tools/` 或 `remote_executor/`

必须同步检查：

- 是否扩大本地或远程执行边界
- 是否改变安全扫描、默认权限、敏感目录写入
- 是否需要更新 `docs/runbooks/security.md`

### 修改跨模块公共接口

必须同步检查：

- 是否需要新增或更新 `docs/architecture/tech-decisions/`
- 是否需要新增或更新 `specs/*/spec.md`

---

## 工厂模式下的依赖纪律

推荐原则：

1. 新逻辑先放到最靠近职责的位置。
2. 不要把临时策略硬塞进 UI 层。
3. 不要把产品规则写成只存在于聊天记录里的“默认常识”。
4. 任何公共行为变化，都要能在 docs 找到对应更新。
