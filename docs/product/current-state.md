# Current State

## 项目综述

当前仓库是一个基于 LangGraph 的多场景安全代理，覆盖 Web、内网、Crypto、Pwn、Reverse、Misc、AI 安全和云安全等方向。

现有代码主干仍保持原目录结构，治理改造通过“加一层文档与统一入口”的方式进行，不强制搬动业务代码。

---

## 当前已经具备的基础

- 有较完整的核心代码与工具目录
- 有一定数量的测试与 GitHub Actions 基础设施
- 有较多历史文档，说明项目并非零过程仓库

---

## 当前主要问题

### 1. 文档分散

历史上的设计、计划、评估文档主要平铺在 `docs/` 根目录，机器很难快速判断：

- 哪份是愿景
- 哪份是当前事实
- 哪份是运行手册
- 哪份只是一次性的历史报告

### 2. 缺少统一入口

在本次改造前，常见操作依赖零散命令、脚本和习惯记忆。

本轮已新增 `Makefile`，但后续仍需要把 CI、runbook 和团队习惯逐步迁移到统一入口。

### 3. 测试与 CI 仍不健康

当前测试和 CI 仍存在历史问题，详细审计见：

- `docs/PROJECT_AUDIT_2026-04-01.md`

在仓库完全进入工厂模式前，必须把测试与 CI 失败显式记录，而不是靠口头说明。

### 4. 安全面默认边界偏弱

仓库包含本地执行、远程执行、凭据处理、文件生成等高风险能力。详细约束与默认权限模型见：

- `docs/runbooks/security.md`

### 5. 审计问题已形成正式修复计划，但尚未执行完

当前已经有正式 spec 用于驱动全面重构与修复：

- `specs/audit-remediation-program/spec.md`

这意味着：

- 审计问题不再只是“报告结论”
- 后续修复应按 workstream 和原子 PR 执行
- 修复完成前，当前风险仍然真实存在

## 当前工作方式

从本次改造开始，推荐工作方式是：

1. 从 Issue 或 Spec 起步
2. 先更新 docs，再改代码
3. 用 `Makefile` 跑统一入口
4. 按原子提交提交和推送

## 与历史文档的关系

新的分层结构是“当前规范层”，而不是对旧文档立即清空重写。

原则：

- 新任务优先写入新结构
- 旧文档保留，逐步归档或吸收
- 具体事实优先更新到对应新目录，而不是继续追加到无分类根文档
