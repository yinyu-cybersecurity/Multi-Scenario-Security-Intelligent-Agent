# Product Vision

## 目标

把这个仓库建设成“可被机器稳定接手的工厂”，而不是依赖聊天上下文、隐式偏好和人类记忆来推进工作的工作区。

这里的“工厂”指：

- 规划在仓库内显式存在
- 任务边界清晰
- 验收可由命令、测试、扫描器直接判断
- 文档分层明确，机器知道该去哪里找事实
- 默认权限最小化，执行与发布分层

---

## 愿景声明

对于任何一个新任务，合格的执行路径应该是：

1. 从 Issue 或 Spec 读取明确目标
2. 从 `docs/product/current-state.md` 读取当前状态
3. 从 `docs/architecture/` 读取系统边界
4. 从 `docs/runbooks/` 读取操作约束
5. 用统一入口执行安装、测试、扫描
6. 以原子提交完成变更并推送远端

而不是：

- 从聊天记录里猜隐含意图
- 通过大量无约束试探来找方向
- 把“经验”放在脑中或会话中而不落库

---

## 非目标

这次仓库治理改造的非目标：

- 不强行重排现有业务代码目录
- 不在这一轮内解决所有测试失败与安全债务
- 不把所有历史文档立即迁移到新目录

当前目标是先搭出机器可接手的骨架，再逐步迁移旧内容。

---

## 成功标准

满足以下条件时，视为仓库在朝“工厂模式”靠近：

1. 每类信息都有固定落点，而不是散落在 README、PR 和聊天记录里。
2. 每个变更都能绑定到 Issue、Spec 或 Runbook。
3. Agent 默认知道该看什么文档、该更新什么文档、该跑什么命令。
4. 提交和推送行为具备纪律，不再把大量未结构化改动堆在本地。
5. 安全与发布权限有清晰分层。
